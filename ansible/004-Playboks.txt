Playbook — это YAML-файл (обычно список объектов-play, начинающийся с ---), который описывает, какие действия и на каких хостах нужно выполнить для достижения целевого состояния.

Верхний уровень Playbook — это список Plays (- name: ...). Каждый Play — это блок настроек и задач для выбранной группы хостов.


hosts, tasks, become, vars, gather_facts
Ключевые директивы на уровне Play (часть из них может переопределяться и на уровне отдельной задачи task):

hosts — целевая группа или список хостов из инвентаря (например, web, db, all).

tasks — упорядоченный список задач (- name: ...), каждая из которых вызывает модуль (ansible.builtin.apt, ansible.builtin.service, ansible.builtin.template и др.).

become (true/false) — включает/выключает повышение привилегий (по умолчанию sudo) для выполнения задач.

vars — локальные переменные внутри конкретного Play (перекрывают переменные инвентаря/групп, но уступают extra_vars).

gather_facts (true/false) — управляет автоматическим сбором фактов о системе (ОС, IP, архитектура, память) в начале Play через модуль setup. Если факты в Play не нужны, gather_facts: false ускоряет запуск.


Plays и Tasks
Play — «сценарий для конкретной роли/группы машин» в рамках запуска (например, Play 1 настраивает db, Play 2 настраивает web).

Task — конкретный атомарный шаг внутри Play (установить пакет, создать каталог, запустить службу).


Внутри одного Play задачи выполняются строго сверху вниз, последовательно — сначала для всех выбранных хостов выполняется task 1, затем для всех хостов task 2 и т.д. (управлять параллелизмом можно параметром serial или strategy). Если на хосте возникает необработанная ошибка (failed), этот хост выпадает из дальнейших задач текущего Play.

Несколько Plays в одном Playbook
Один .yml-файл может содержать несколько последовательных Plays:

YAML
---
- name: Настройка базы данных
  hosts: db
  become: true
  tasks: ...

- name: Настройка веб-узла
  hosts: web
  become: true
  tasks: ...
Сначала полностью отработает первый Play (на db), и только потом начнётся второй Play (на web). Это удобно для межсервисной оркестрации, когда БД должна быть поднята до настройки клиента.


import_playbook и повторное использование Playbook
Директива ansible.builtin.import_playbook позволяет включать один playbook внутрь другого (статически, на этапе парсинга Playbook).

YAML
---
- name: Импорт настройки БД
  ansible.builtin.import_playbook: playbooks/db.yml

- name: Импорт настройки Web
  ansible.builtin.import_playbook: playbooks/web.yml
Зачем нужно: разбивать монолитный сценарий на понятные файлы (db.yml, web.yml, site.yml), переиспользовать готовые playbook'и в разных пайплайнах.


import_playbook нельзя использовать внутри tasks: — это директива верхнего уровня (на уровне Plays), и внутри импортируемого файла должен быть валидный Playbook (список Plays), а не просто голый список задач. (Для динамического включения задач внутри tasks: используются include_tasks / import_tasks, а для крупного переиспользования — роли).
